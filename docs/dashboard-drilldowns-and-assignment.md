# Metric drilldowns, sample evidence and scan assignment

The six daily dashboard metrics and their Yesterday comparisons open detail lists based on the same membership predicates as their counts: due orders, proof-dated deliveries, remaining scheduled deliveries, completed pickup tasks, late deliveries and late pickup tasks. Pickup counts count tasks, not unique orders, so one AWB can appear multiple times for multiple vendors. Drilldown rows open the scoped order/proof dialog. Driver profile counters also open exact current/recorded-work lists; fleet assigned/pending/delivered numbers are interactive. Dashboard driver, active-trip and location-flag totals link to their corresponding details; charts retain their existing drilldowns. These are snapshots from the current authorised state, not a fresh background query that can disagree with the displayed number.

A generated fictional gift-box/bouquet image and a graphic labelled FICTIONAL DEMO SIGNATURE — NOT REAL are shared local assets. The image is generated sample imagery, not a real customer delivery photograph. `demo-media.js` enriches only records marked demoData with MAWADA-DEMO references, and only adds proof images/signatures to proof records explicitly marked simulated. Existing real evidence is never replaced. The normal startup compatibility pass upgrades earlier seeded demo records; new sample packs include media immediately. The isolated browser demo is entirely fictional and gets the same illustrative sample assets. Item images appear in marked sample order cards and details. Static asset URLs are allowlisted in the proof viewer; real uploads retain existing validated data-image handling. Shared URLs avoid duplicating image blobs in the database or every polling response.

Scan & assign is a separate admin/operations workspace requiring existing work permission. It reuses the AWB scanner, image/USB/manual input and deduplicated queue (100-order cap). Choose a driver and either all incomplete vendor pickups or delivery assignment. Each command uses the existing server-authorised action routes, prevents active-trip reassignment and records the assigning actor. It is not an atomic multi-order transaction: individual failures are shown and partial pickup changes must be checked before retrying. Successful queue items are removed. Delivery assignment itself is distinct from dispatch; existing complete-item/warehouse checks still gate departure. Assignment does not automatically dispatch, collect or deliver anything. The isolated demo mirrors the same basic active-trip/delivered reassignment guards.

Drivers continue to self-assign through Scan / claim AWB in their mobile workspace. Claims cannot steal already assigned work; delivery claims require the complete order at the warehouse. No new driver permission expansion is introduced.

Validation covers count/list parity (including two vendors on one order), preservation of real evidence and idempotent sample-media upgrades, today/yesterday drilldown UI, manual scan assignment and existing driver self-claim and no-stealing scenarios. Live database sample upgrades and device camera behaviour remain subject to deployment/device verification.
