# Team login and access

The live app at `/` uses server accounts with hashed passwords and server sessions. `/demo` is an isolated fictional browser-session demo: role selection is a simulation, not a login. Earlier demo team creation discarded passwords and could not create real login accounts; it is now disabled with a live-app link. Those sample entries cannot be converted into real accounts; create the account in the live app's Team access page. Signing out of the demo now navigates out to `/` instead of reloading into the demo administrator.

Live login normalizes email case and surrounding spaces, regenerates the session and explicitly saves it before responding. Logout destroys the server session and clears its cookie; failures produce an error rather than a false success. Automated API checks cover logout, rejection of the previous session and signing back in. Hostinger login/cookie behaviour still requires live verification. Sessions remain in-memory and expire on a process restart; a persistent session store remains separate production work.

Administrators create team members with a role and feature-access checklist, and can edit existing non-administrator checklists. The feature gates are dashboard/fleet monitoring, reports/exports, create/import orders, manage vendors and operational actions (assignment, claims, scans, statuses, proof). Gates apply on the server as well as navigation. They restrict existing role powers and never expand them: drivers remain limited to assigned work/available claims, warehouse users to warehouse-role actions, and operations users to their existing operational rights. Administrators always have full access and manage the team; this cannot be unchecked to cause lockout. This is a feature checklist per account based on role defaults, not a globally editable role-definition system or field-level privacy engine. Users with revoked feature access can still read order records within their existing role scope.

Existing accounts without a permissions array retain the original role defaults. Changes affect subsequent requests because the server reads the current user record on each request. Changes are recorded with administrator ID, timestamp and permission list (last 100 edits). No database migration is necessary in either SQLite or Supabase JSON records. Demo permission editing is disabled and clearly labelled rather than pretending to secure sample data.

## Add, edit and delete users

Administrators have Create team member, expandable Edit account forms (name, email, role and optional new password) and Delete user controls in Team access. Non-admin requests to these endpoints are denied. Demo editing/deletion remains disabled. Passwords need at least 12 characters, are hashed and are never included in edit history. Email uniqueness includes deleted accounts; deleted emails are reserved, not silently reused.

POST /api/users/:id/edit records before/after name, email and role, editor, timestamp and a password-reset flag. A role change restores the new role defaults; update its permission checklist afterwards if needed. Password/role changes increment an authentication version checked against every session on the next request. An administrator changing their own password keeps the current session, while other sessions become invalid. An administrator cannot remove their own admin role.

POST /api/users/:id/delete removes access and hides the account from active team/fleet lists. It is a logical deletion, with deletedAt/deletedBy retained alongside historical identity for proofs and reports; not a physical erasure of audit records. Existing sessions and new login attempts are rejected. Self-deletion is blocked, so at least the acting administrator remains. Deletion and role changes are blocked while an account owns open delivery work, incomplete pickups or in-transit trips; reconcile/reassign that work first. No storage schema migration is required.

API checks cover non-admin denial, editing and password reset, old-session revocation, updated credentials, self-demotion/deletion rejection, active-driver deletion rejection, and deleted-user login/session denial. These are prototype safeguards, not a general cross-record transactional identity/assignment engine; administrators should finish reassignment before editing/deleting an operational driver.
