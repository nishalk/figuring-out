# Driver activity, order proof and AWB printing

## Driver activity and location

Drivers can Start shift / End shift from their workspace. Start records a server timestamp and requests foreground GPS sharing; the shift can still start if browser GPS is unavailable, and the error/paused state remains visible. Ending requires active trip legs to be reconciled first, records a server timestamp and stops foreground sharing. Existing trip workflows do not require a new shift, preserving existing operation contracts.

Fleet control → View driver shows shift times, latest GPS timestamp/accuracy, a movement map, timestamped GPS log and actions attributable to the driver's ID. GET /api/fleet/:id/activity requires admin/operations plus dashboard monitoring permission. Drivers cannot request another driver's history. It returns up to 500 most recent combined activity/order events and at most 2,000 GPS fixes from the last 24 hours. Account activity is capped at 500 entries; order histories retain their existing lifecycle. Account activity records login/logout, shift changes, sharing changes, successful AWB lookup and label-preview actions; order history records claims and operational actions with actor IDs. GPS samples are a separate timestamped trace. This is an operational audit, not a record of every screen tap, rejected attempt or browser interaction; older actions without actor IDs are not guessed/backfilled. Historical locations cannot be reconstructed before tracking began. Fresh reported GPS is attached to driver order actions when a server-known fix is at most two minutes old.

Maps show reported GPS fixes, not a verified road route. Segments separated by more than two minutes are not joined. First retained and latest GPS markers include timestamps. This can include inaccurate fixes; consult accuracy and existing discrepancy flags. Positions refresh on the existing 30-second visible dashboard/order polling cycle. User GPS collection remains foreground-only: an open driver browser, permission and connectivity are required. Android background/locked-phone tracking, continuous guaranteed live streaming and historic road-route playback are not implemented. No new fake map coordinates are inserted. Existing simulated demo locations stay clearly sample data.

## Order details and proof

Clickable AWBs on order cards, reports, driver shipment rows, driver activity and label queues open the scoped order-detail dialog using the already authorised state data. It shows receiver/contact/address, items, quantities, vendor names, delivery notes and history. Available pickup/delivery photos, recipient signature, acknowledgement name/time and coordinates are shown. Missing evidence is labelled missing, not manufactured. Demo simulated proofs remain labelled. Coordinates have a Leaflet pin and an external OpenStreetMap link. No unauthenticated public tracking/proof endpoint is created. Existing role query scope is preserved.

## Labels

AWB printing is a separate navigation tab. Choose orders via manual AWB list, USB/Bluetooth scanner input, camera or a barcode image (max 5 MB). Duplicate scans are ignored. Invalid/inaccessible AWBs report not found without looking up other users' work. Select current order filter respects existing status/search; at most 100 labels can be queued and rendered in one batch. Camera resets on navigation, backgrounding and preview. Permission denial/manual fallback remains available.

Individual Print AWB label actions and the order-detail print action use the same renderer. Labels include Mawada heading, Code128 barcode/human-readable AWB, order reference, receiver name/phone/address, date/slot, item-line and total-unit counts, item/vendor quantities, bell/card preferences and extra directions. Prices, sender details and signatures are not printed. There is no package-level barcode or separate package-count field: quantities are item units and clearly labelled. Blank data is explicitly not specified. Browser print dialog provides printer/PDF selection; each order starts a new page. Barcode loading must finish before Print is enabled, and an image error leaves printing disabled. Printing cancelled in the browser is not represented as a successful physical print. The server logs authorised label preview intent, not printer completion.

The live preview audit endpoint verifies all order IDs against the caller's existing role scope. Drivers remain limited to assigned pickup/delivery orders, including completed assigned orders. There is no new permission grant or public access. Static sample demo previews stay local.

Validation: API tests cover start/end shift, active-trip blocking, operational/account activity, GPS availability, monitoring permission denial and scoped label audit. Browser tests exercise opening delivered orders, recipient signatures, proof pins, manual duplicate AWBs, real Code128 image scanning, multi-label preview and existing printing/PDF flow. Public map tiles are stubbed in browser checks; real device GPS, printer output, live Hostinger deployment and map-provider availability require device/deployment checks.
