# Connect the existing Hostinger Supabase project

Hostinger's connection wizard alone does not change the app's storage. Integration is opt-in. SQLite remains active unless `DATABASE_BACKEND=supabase` is explicitly set. No existing SQLite accounts, orders, or proof files are automatically migrated or deleted.

1. Open the connected project in Supabase. In **SQL Editor**, create a new query and run the complete contents of [`supabase/schema.sql`](../supabase/schema.sql). This creates a dedicated `delivery_records` table with unique identifiers, optimistic update revisions and row-level security enabled. Browser roles have no access; this app uses its own server-side login and permissions rather than Supabase Auth.
2. In Hostinger's environment settings, check the names of the injected bindings. The app accepts `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY`, or Hostinger's `SUPABASE_API_KEY` only when it is a server-only secret key or legacy service-role key. A public/anonymous/publishable key cannot access this table and is rejected. Obtain the appropriate key from the connected project's API settings and enter it only in the Hostinger secure editor. Do not put a server key in frontend variables, screenshots, Git, or chat. Keep the existing `NODE_ENV`, `SESSION_SECRET`, and `SETUP_KEY` values.
3. Preserve existing SQLite data before changing backends. If there are any accounts/orders to retain, stop here and plan an explicit export/import; don't assume a Git redeploy preserves local SQLite files. For an empty/disposable trial, select the new backend by adding `DATABASE_BACKEND=supabase` to Hostinger and redeploy. The app will fail closed on missing schema/credentials; it never silently falls back to SQLite.
4. Open the app. An empty Supabase table requires initial administrator creation with the existing setup key. Log in and check that the administrator dashboard says **Cloud database: Supabase**. Create a dummy vendor/order, redeploy, sign in again and verify both still exist. This is the live retention check; local adapter tests do not establish that the Hostinger project's schema or keys are configured.

Current design stores proof images inside each order's JSON record, as SQLite did. This is suitable for a small dummy trial only; paginated queries still load whole order records. Large-scale use needs private object storage, narrower queries, and retention controls. Sessions and throttles now persist locally in `DATA_DIR/runtime.db`, so a verified persistent volume is still required even when operational data is remote. No Supabase schema change is required for the new controls. Configure provider-managed database backups and test recovery; the local SQLite backup tool explicitly does not back up Supabase. See [service configuration](service-configuration.md).

Verification: unit/integration tests exercise both SQLite and the Supabase SDK against a local PostgREST test server, including multi-page reads, revision conflicts and atomic batch rejection. No live project connection, RLS execution, data migration or Hostinger persistence is claimed until separately verified.
